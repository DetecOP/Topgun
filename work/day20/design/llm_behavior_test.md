# ทดสอบพฤติกรรม LLM ของผู้จัด (event-llm) ก่อนให้สั่งงาน · ผู้ออกแบบ (Session B) · 19 พ.ย. 2026

**กติกาที่ผู้จัดตอบ (ผู้ใช้แจ้ง 19 พ.ย.)**: ระหว่างแข่งห้ามใช้ LLM อื่น · ใช้ได้แค่ LLM ของผู้จัด (gateway)
→ วันแข่ง Session B (Claude) **ไม่วิเคราะห์ข้อมูลรอบสด** · การช่วยตัดสินใจระหว่างแข่งมีได้ 2 ทาง: (1) คนอ่านตาราง DAY3 หัวข้อ 6 (2) event-llm ผ่าน agent
→ ก่อนสั่ง event-llm ได้ถูก ต้อง "เทรน" = **วัดพฤติกรรมของมันให้รู้ว่าเข้าใจอะไรถูก/ผิด แล้วแก้ prompt** (fine-tune ไม่ได้)

ไฟล์นี้ต่อจาก `llm_plan.md` (หัวข้อ 2 รายการป้าย · หัวข้อ 4 การต่อเข้า agent) · ทุกการเรียกไปที่ gateway เท่านั้น · **ไม่มีขั้นไหนส่งซองเข้าตลาด**

## G0 · ตัวตรวจแบบกฎ `rule_advisor` (ไม่ใช้ LLM)
```
def rule_labels(model, state) -> {type: label}:      # ป้ายชุดเดียวกับ llm_plan หัวข้อ 2
    สำหรับแต่ละประเภท (C/I/S):
      lost2   = เราแพ้ (OUTBID) ประเภทนี้ ≥ 2 รอบติด
      sold_all= รอบก่อนเราขายครบทุกซองประเภทนี้
      short2  = fill < 0.5 สองรอบติด และมีล็อตผ่านสเปก
      flood   = sellable > capacity ที่เหลือ
      fest    = รอบนี้อยู่ในช่วงเทศกาล และ Specialty ใบใหญ่กว่าค่าเฉลี่ย R1–R5 ≥ 1.5 เท่า
      ลำดับ: flood → undercut(lost2) → shortage(short2 และไม่ lost2 ล่าสุด) → festival_surge(fest) → normal
พิมพ์ทุกรอบ: "แนะนำ: COMMERCIAL=normal · INSTANT=undercut → $env:MKT_K_INSTANT='2.0'" + เหตุผล 1 บรรทัด
log: rule_advice {round, labels, reasons}
```
test: 1 ข้อต่อป้าย (5 ข้อ) + ข้อ "ไม่เปลี่ยนซอง" (เปิด/ปิด advisor ซองต้องเหมือนกันทุกตัว)

## G3 · ชุดทดสอบพฤติกรรม (T1–T6)
ค่าคงที่ทุกข้อ: temperature 0 · max_tokens 200 · thinking ปิด · schema ป้ายแบบ enum (llm_plan หัวข้อ 3 ข้อ 2)

| ข้อ | ทดสอบอะไร | วิธี | เกณฑ์ผ่าน |
|---|---|---|---|
| T1 รูปแบบ | ตอบ JSON ตาม schema · ค่าอยู่ใน enum · ตอบซ้ำเหมือนเดิม | prompt เดียวกัน 10 ครั้ง | JSON ถูก ≥ 95% · enum ถูก 100% (หลังตัวตรวจ) · ตอบเหมือนกัน ≥ 9/10 |
| T2 เข้าใจสัญญาณ (**ตรงจุดที่พลาด 18 พ.ย.**) | ความหมาย OUTBID / ABOVE_LIMIT / fill < 50% · ทิศราคาที่ถูก | คำถามเลือกตอบ 8 ข้อ × 3 ครั้ง เช่น "รอบก่อน OUTBID ควร: ขึ้น/ลง/คงราคา" | ถูก ≥ 7/8 ทุกครั้ง · **ข้อทิศราคาหลัง OUTBID ต้องถูก 3/3** |
| T3 จำแนกสถานการณ์ | ป้ายบนชุดสอบ 19 จุด | เทียบเฉลย และเทียบ `rule_labels` | % ตรงเฉลย ≥ ของกฎ · **ผิดทิศ = 0** (ผิดทิศ = เลือก shortage/ขึ้นราคา เมื่อเฉลย undercut หรือกลับกัน) |
| T4 รูปแบบ prompt | prompt แบบไหนเข้าใจดีสุด | ชุดสอบเดียวกัน 4 แบบ: A สถานะดิบ · B ข้อเท็จจริงที่ Python ตีความแล้ว (`we_lost_last_round: yes`) · C = B + ตัวอย่าง 8 จุด · D = C ภาษาไทย | เลือกแบบที่ T3 ดีสุด · ถ้าเสมอเลือกแบบสั้นสุด |
| T5 ความนิ่ง | ไม่เปลี่ยนคำตอบเมื่อสิ่งที่ไม่เกี่ยวเปลี่ยน | ชุดสอบเดิม สลับลำดับประเภท · ใส่ตัวเลขไม่เกี่ยว 1 บรรทัด | ป้ายเปลี่ยน ≤ 1/19 |
| T6 เวลา | latency และการล้ม | ทุกคำขอใน T1–T5 | p95 < 20 วิ · ล้ม/timeout ≤ 5% |

T2 ตัวอย่างคำถาม (Python ให้คะแนนเอง):
1. รอบก่อนเรายื่น ×1.00 แล้ว OUTBID แปลว่า: (a) ทีมอื่นขายถูกกว่า (b) เกินเพดานผู้ซื้อ (c) ไม่ผ่านสเปก → a
2. ต่อจากข้อ 1 รอบนี้ควร: (a) ขึ้นราคา (b) ลดหรือคงราคา → b
3. ABOVE_LIMIT แปลว่า → เกินเพดานลับของผู้ซื้อ · ควรลด
4. ผู้ซื้อซื้อได้ 40% ของที่ต้องการ 2 รอบติด ซองเข้าน้อย และเราขายครบ → ของขาด อาจขึ้นได้
5. ผู้ซื้อซื้อได้ 40% แต่เรา OUTBID → ไม่ใช่ของขาดสำหรับเรา ห้ามขึ้น
6. ของเหลือ 20 กระสอบ capacity ที่เหลือ 15 → flood
7. ของเหลือ 5 กระสอบ capacity ที่เหลือ 30 → ไม่ใช่ flood
8. ของที่ขายไม่ได้ได้ 0.80 × TV · ขายที่ 0.79 ดีกว่าไม่ขายไหม → ไม่

## G4 · "เทรน" = แก้ prompt จากข้อผิด (≤ 3 รอบ)
ทุกรอบ: ดูข้อที่ผิดใน T2/T3 → แก้ prompt อย่างใดอย่างหนึ่ง: เพิ่มกฎชัดใน system (เช่น "OUTBID never means raise") · เปลี่ยนตัวเลขดิบเป็นข้อเท็จจริงที่ตีความแล้ว · เพิ่ม/เปลี่ยนตัวอย่าง → สอบ T2/T3 ซ้ำ
- เก็บทุกเวอร์ชันใน `work/day20/llm_eval/prompts/v1..v3.txt` + ผล · จำกัด 3 รอบเพราะชุดสอบมี 19 จุด แก้มากกว่านี้ = จำข้อสอบ
- ห้ามแก้ตัวตรวจทิศทาง (direction_guard) ให้หลวมลงเพื่อให้ LLM ผ่าน

## G5 · วงปิดตลาดจำลองด่าน 3
`LLM_MODE=label` vs `rule` (ป้ายจาก `rule_labels` ใช้ชุดค่าเดียวกัน) vs ไม่มีป้าย · seed เดียวกัน 30 เกม (15 คำขอ/เกม ≈ 30 นาทีที่ 20/นาที)
- 30 เกมแยกผลเล็กไม่ได้ → เกณฑ์คือ **"ไม่แย่กว่า rule เกิน 2 SE"** และ "ผิดทิศ 0 ครั้ง" (ตัวกันทำงาน = นับครั้งที่ตัวกันต้องทิ้งป้าย)
- ถ้า rule เองแย่กว่าไม่มีป้าย → ป้ายทั้งระบบไม่ช่วย → ทั้ง rule และ LLM ใช้แค่ "พิมพ์คำแนะนำให้คน" ไม่มีผลกับ agent

## รอบ 2 · คำตัดสินจากผล G0/G1/G2 (19 พ.ย.)

ผล A: G1 พอร์ต 4001 ปฏิเสธการต่อ = gateway ยังไม่เปิด · G0 `rule_advisor.py` เสร็จ (test 65/65) · G2 ได้ 24 จุด แต่เฉลย = `normal` ทั้ง 24 จุด

**G2: หยุด ไม่สร้างชุดสอบเพิ่ม**
- เห็นด้วยกับ A: ข้อเท็จจริงมาจากเส้นทางจริงด่าน 2 (โค้ดเก่า R1–R2 ขาย 0 → flood จริง) แต่เฉลยมาจากเส้นทาง replay ของ market3 (ขายหมด ไม่เคย flood) → คนละสถานการณ์ เฉลยไม่มีความแปรปรวน วัดความแม่นไม่ได้
- ไม่สร้างใหม่จากเส้นทาง replay (ไม่ใช่พฤติกรรมผู้ซื้อจริงต่อซองเรา) และไม่สร้างจากตลาดจำลองตอนนี้ (gateway ปิด ทดสอบ LLM ไม่ได้อยู่ดี · ตลาดจำลองมีสมมติฐานของเรา)
- เก็บ `cases.jsonl` ไว้ใช้เทียบกับคำตอบ LLM ในโหมดเงาหลังแข่ง

**LLM วันแข่ง: `off` (`USE_LLM=0`)** เปลี่ยนจากตารางเดิม (shadow) เพราะ
- ทดสอบ T1–T6 ไม่ได้เลย · โหมดเงาไม่มีผลกับคะแนน แต่เพิ่มโค้ดใหม่ที่ไม่เคยรันกับ gateway จริงในคืนก่อนแข่ง
- ยกเว้น: ถ้าโค้ดโหมดเงาเสร็จแล้ว และมี test "ซองเปิด/ปิดเงาเหมือนกันทุกตัว" ผ่าน → เปิด shadow ได้ เพื่อเก็บข้อมูลพฤติกรรม event-llm ไว้เทรนรอบหน้า · ถ้ายังไม่เสร็จ ไม่ต้องทำ

**rule_advisor: คงไว้ (พิมพ์อย่างเดียว) · กฎให้คนทำตามคำแนะนำ**
ข้อมูลจาก G2: ทุกชุดค่าของป้ายทำให้ replay market3 เท่าเดิมหรือแย่ลง → คำแนะนำไม่ได้ช่วยในสถานการณ์ปกติ ใช้เฉพาะตอนสถานการณ์ผิดปกติจริง

| คำแนะนำ | คนทำตามเมื่อ |
|---|---|
| `flood` | ทำตามได้ทันที — เงื่อนไขเป็นเลขคณิตแน่นอน (ของเหลือ > capacity ที่เหลือ) · ใน market3 ควรเกิดน้อย ถ้าเกิดแปลว่าแพ้มาหลายรอบจริง |
| `undercut` | ขึ้นซ้ำ 2 รอบติด **และ** ของเหลือ > 60% ของ capacity ที่เหลือ · ไม่งั้นไม่ทำ (แพ้แต่ยังมีเวลาขาย = ปล่อยให้ agent ปรับราคาตามตลาดเอง) |
| `shortage` | ขึ้นซ้ำ 2 รอบติด และเราขายครบในประเภทนั้น → `SHORT_CEIL=1` · ถ้ารอบถัดไปแพ้ → ถอดออก |
| `festival_surge` | ไม่ต้องทำ (คำแนะนำ = ไม่เปลี่ยน) |

ถ้ายังมีเวลา (ไม่บังคับ): จำลองด่าน 3 จับคู่ 300 เกม "ทำตามคำแนะนำอัตโนมัติด้วยกฎตารางนี้" vs ฐาน · ถ้าแย่กว่าฐานเกิน 2 SE → วันแข่งทำตามแค่ `flood`

### รอบ 2.1 · ผลข้อ 4 (RULE_AUTO 300 เกม): **ใช้ตารางเต็มวันแข่ง · คนทำตาม · RULE_AUTO คงค่าเริ่ม 0**
ผล: ค่าเฉลี่ย −0.0001 ถึง +0.0011 (ไม่ต่างจากฐานเกิน 2 SE ที่ไหน) · เกมแย่สุดดีขึ้นทุกตลาด (เช่น 0.827 → 0.860)
- ตารางเต็มปลอดภัย → คนเฝ้าจอทำตามได้ทุกแถว
- ไม่เปิด RULE_AUTO เป็นค่าเริ่ม: ค่าเฉลี่ยไม่ดีขึ้นชัด และเป็นโค้ดที่เพิ่งเขียนวันนี้ ยังไม่เคยรันกับตลาดจริง · ผลได้จริงคือกันเกมแย่ ซึ่งคนทำตามตารางได้เหมือนกัน (ช้ากว่า 1 รอบ)
- สวิตช์สำรอง: ถ้าวันแข่งคนเฝ้าจอตามไม่ทัน หรือต้องรีสตาร์ทบ่อย → รีสตาร์ทพร้อม `$env:RULE_AUTO="1"` (A เพิ่มแถวนี้ใน DAY3 หัวข้อ 6)

## รอบ 3 · คำตัดสินโหมด LLM วันแข่ง (หลัง gateway ฝึก :4000 เปิด)

ผล A: prompt v3 ผ่าน T1/T2/T3/T5/T6 (T3 20/20 ผิดทิศ 0 · T6 p95 0.94 วิ) · v1 (ตัวเลขดิบ) ผิดทิศแบบเดียวกับ 18 พ.ย. → ยืนยันว่าปัญหาเดิมมาจากให้ LLM ตีความตัวเลขเอง · วงปิด 10 เกม: ป้ายที่ใช้ = ป้ายกฎ 450/450 · llm_label − rule_auto +0.0016 ± 0.0017 (= ไม่ต่าง)

**ตัดสิน: วันแข่ง `LLM_LABEL=shadow`** (ไม่ใช่ `label`)
- `label` ให้ผลเท่ากับ RULE_AUTO ทุกครั้ง (450/450) แต่เพิ่มการพึ่ง gateway ที่ยังไม่เคยทดสอบ (:4001) · และเราตัดสินแล้วว่า RULE_AUTO = 0 (คนทำตามตาราง) → เปิด `label` = ขัดกับคำตัดสินนั้นโดยไม่ได้อะไรเพิ่ม
- `shadow` ได้: ข้อความอธิบายลง log (ช่วยคนเฝ้าจอ/อธิบายกรรมการ) + ข้อมูลพฤติกรรม event-llm ตอน 56 ทีมใช้พร้อมกัน (เทรนรอบหน้า) · ความเสี่ยงต่ำเพราะถามหลังส่งซองแล้ว
- ทางสำรองเมื่อคนตามไม่ทัน ยังเป็น `RULE_AUTO=1` (ไม่พึ่ง LLM) ไม่ใช่ `label`

**เงื่อนไขเปิด shadow (ครบทุกข้อ ไม่ครบ = `off`)**
1. test "เปิด/ปิด shadow ซองเหมือนกันทุกตัว" อยู่ใน 70 ข้อและผ่าน (A ยืนยัน)
2. ตัวคุมอัตราที่แก้แล้ว (≥ 4 วิ/คำขอ · 429 พัก 60 วิ) มี test และไม่ใช้ `time.sleep` ที่ตลาดจำลองปิดได้
3. P1–P2 วันแข่ง: :4001 ตอบ · p95 < 20 วิ · ไม่มี error ต่อเนื่อง · ถ้าไม่ผ่าน → รีสตาร์ทพร้อม `$env:LLM_LABEL="off"` (ทำได้ระหว่างรอบซ้อม ไม่เสียอะไร)
4. ระหว่างแข่ง ถ้าเห็นเวลาส่งซอง (`offers_sent.seconds`) ช้าขึ้นผิดปกติ หรือ agent ค้าง → `off` ทันที
